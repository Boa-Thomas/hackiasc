# Schema Bootstrap

`bootstrap.sql` is a single, idempotent script that recreates the **entire `public` schema** of
the HackIA production database (project `qshrzfahotmjshtjuvno`) on a **fresh Supabase project** —
in one run. It is generated **verbatim from the live prod catalog** (the source of truth; the
historical `migrations/` had drifted), so a new edition starts from an exact copy of the proven schema.

This is sub-project #1 of the [multi-edition architecture](../docs/MASTER-PLAN.md): each future
HackIA edition gets its **own isolated Supabase project**, stood up with this script.

## How to provision a new edition's schema

1. Create a fresh Supabase project.
2. Run `bootstrap.sql` against it (SQL Editor, or `psql "$DATABASE_URL" -f bootstrap/bootstrap.sql`).
   The script sets `check_function_bodies = false`, so object order never blocks it, and every
   statement is idempotent (`CREATE … IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP POLICY … / CREATE POLICY`,
   `INSERT … ON CONFLICT DO NOTHING`), so it is safe to re-run.

That gives you: 9 extensions, 37 tables, 155 functions, 111 constraints, 52 indexes, 10 triggers,
RLS enabled + 67 policies (61 public + 6 storage), table/function grants, the `files` storage
bucket + its policies, and the 3 structural singleton rows (`mp_sync_status`, `wall_state`, `slides_config`).

## What this does NOT cover (still owned by the runbook — sub-project #4)

`bootstrap.sql` stands up the **database schema only**. A working edition still needs:

- **Edge functions (14):** `create-preference`, `mp-webhook`, `refund-payment`, `sync-mp-payments`,
  `evaluate-team`, `mp-webhook-secret-check`, `resource-download`, `team-slides`, `transcribe-pitch`,
  `send-push`, `access-exchange`, `access-admin`, `access-account`, `log-event`
  (`supabase functions deploy`).
- **Secrets / vault** (per instance): Mercado Pago access token, `PUSH_WEBHOOK_SECRET` + VAPID keys,
  `WHISPER_URL`, and the vault secrets `edge_anon_key` / `push_webhook_secret` used by
  `trg_notifications_send_push`. (Supabase service-role key is auto-provisioned.)
- **Scheduled jobs / cron** (e.g. `sync-mp-payments` polling).
- **Deploy env + DNS:** frontend env vars (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) and the
  edition subdomain (Cloudflare Pages).

## Layout & regeneration

`parts/` holds the generated category files, concatenated in dependency order into `bootstrap.sql`:

```
00_header → 10_extensions → 20_tables → 30_functions → 40_constraints → 45_indexes
→ 50_triggers → 55_rls_enable → 60_policies → 70_grants → 80_storage → 90_seed
```

Each part is generated by querying `pg_catalog` / `information_schema` on live prod and base64-encoding
the result (byte-exact transport). To regenerate after the prod schema changes, re-run the generators
documented in [`docs/superpowers/plans/2026-06-03-schema-bootstrap.md`](../docs/superpowers/plans/2026-06-03-schema-bootstrap.md)
and re-`cat` the parts.

## Verification status

Verified against prod (2026-06-03) by **structural parity** (object counts match exactly) and
**byte-exact fidelity** (per-category `md5` of the generated parts equals the live prod catalog).
Full execution on an *empty* database (dependency ordering) was not run — that would require a
throwaway Supabase branch; mitigated by `check_function_bodies = false`, the dependency-safe part
order, and a pre-flight confirming no column default calls a custom function.
